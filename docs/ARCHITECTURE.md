# Architecture

Inbox Triage is three iPhone Shortcuts generated by one Python script, plus a few Mac tools. The shortcuts hold no settings and no secrets: they read everything from iCloud Drive at run time. That way, rules and prompts can change without re-importing, and agents on a laptop can tune them.

## The three shortcuts

| Shortcut | Actions* | Job |
|---|---|---|
| **InboxTriage Token** | ~50 | Reads `iCloud Drive/.config/inbox-triage/secrets.json`, exchanges the refresh token for a one-hour access token at `oauth2.googleapis.com`, and outputs it. It is the only shortcut that touches the secrets. |
| **InboxTriage Engine** | ~950 | The triage run. It takes an optional dictionary of per-run overrides as input. |
| **InboxTriage** | ~650 | The front end: the menu, the Kept view, Custom runs, and feedback (share-sheet target). |

\* About a third of the actions are structural: If, Otherwise, End If, Repeat, menu items and comments.

They call each other with **Run Shortcut** by name, so they must be imported with exactly these names.

## A Default run (Engine)

1. **Load.** `config.json`, `rules.json` and `prompts/*.txt` from `iCloud Drive/Shortcuts/EmailTriage/`. Per-run overrides from the input dictionary replace config values: Custom runs set the batch size, hours, extra search, dry run and switches, and feedback runs pass message ids with forced decisions.
2. **Token.** Run **InboxTriage Token**.
3. **List.** `GET users/me/messages?q=<query> older_than:<ignoreHours>h -label:autotriage-kept <extra>&maxResults=<n>`. It also counts the kept messages still in the inbox ("Bypassed").
4. **Per message:**
   1. `GET messages/{id}?format=metadata` for From, Subject, Date, Message-ID, List-Unsubscribe and List-Unsubscribe-Post, plus the snippet, labels and threadId. Keys are read one level at a time (see [LESSONS.md](LESSONS.md)).
   2. **Sender rules**, then **content keyword rules** (`rules.json`). The last match wins, and content rules win over sender rules.
   3. Otherwise **Use Model** (Apple on-device), with the system, category, rule and content-rule prompts plus a filled-in message template. It returns JSON: action, level, flag, confidence and reason. The reply is validated, and low confidence, IMPORTANT or STARRED become KEEP.
   4. **Thread collapse.** Messages arrive newest first, so a KEEP in a thread that already has a kept message is an older one and is archived.
   5. **Op.** keep, archive or trash, depending on the decision and the switches (see the README).
   6. **SUMMARIZE.** `GET messages/{id}?format=full`. A regular expression over the raw JSON finds the first `text/plain` part at any depth, else `text/html` (converted to text), else the snippet. The base64url body is padded and decoded, cut to 3000 characters, and summarized with `prompts/summary-<level>.txt`. A confirmation whose summary comes back as `HIGH` is summarized again at high.
   7. **UNSUBSCRIBE.** An RFC 8058 one-click POST to the https URL (no Gmail token), or a Gmail draft to the mailto address. Otherwise a manual link in the report.
   8. **Gmail.** Unless dry run: keep adds `INBOX` and `AutoTriage/Kept`; archive removes `INBOX` and `AutoTriage/Kept` and adds `AutoTriage`; trash adds `AutoTriage` and then calls `/trash`.
5. **Report.** A Markdown note created with Notes' Create Note action (`WFCreateNoteInput`, `interpretAsMarkdown`) and opened. The same text is saved to `log/last-report.txt`, and a tab-separated machine log to `log/last-run.txt`.

## Feedback (InboxTriage)

A report note shared to InboxTriage arrives as text. Each line tagged `x?<hint>)` is parsed with regular expressions (`bin/build-shortcut`, tested in `tests/test_patterns.py`):

1. Record the correction in `feedback/pending.tsv` (date, note, id, original, corrected, line).
2. Ask **Locally AI** (Ternary Bonsai 2 9B, a local model) for proposed sender and content rules, given the corrections, your hints and the current `rules.json`. The reply is shape-checked with patterns only and saved to `feedback/proposed-rules.json`. It is never applied.
3. Run the Engine on just those ids with the decisions you chose.
4. Mark them in `feedback/applied.txt`, so sharing the same note again does nothing.

`bin/learn` (Mac) reads `pending.tsv`, looks up sender addresses in Gmail, and proposes a reviewed diff of `rules.json`. `--apply` writes `local/rules.json` and deploys.

## Files

```text
iCloud Drive/
  .config/inbox-triage/secrets.json          CLIENT_ID, CLIENT_SECRET, REFRESH_TOKEN (never in the repo)
  Shortcuts/EmailTriage/
    InboxTriage*.shortcut                    signed builds to import
    config.json  rules.json  prompts/*.txt   read at run time
    log/last-run.txt  log/last-report.txt    last run only
    feedback/pending.tsv  applied.txt  proposed-rules.json
```

## The generator

`bin/build-shortcut` is a small DSL over Python dicts. It has helpers for text tokens, variable attachments, typed variables, If/Repeat/Menu blocks and app-intent actions, and emits the three plists with `plistlib`. `shortcuts sign --mode anyone` signs them. Action identifiers and parameter keys come from:

- Apple's own Gallery shortcuts (`WorkflowKit.framework/.../Gallery.bundle/*.wflow`)
- app-intent metadata (`Metadata.appintents/extract.actionsdata`) for Mail and Notes
- an exported test shortcut (Locally AI)
- the [Cherri](https://github.com/electrikmilk/cherri) compiler's action definitions
- community notes ([viticci/shortcuts-playground-plugin](https://github.com/viticci/shortcuts-playground-plugin), [danielhopkins/apple-tools](https://github.com/danielhopkins/apple-tools))

`tests/test_generator.py` turns every failure seen on the phone into an invariant over the generated plists.
